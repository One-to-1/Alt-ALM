## Risk register

| ID | Risk | Likelihood | Impact | Mitigation | Trigger / monitor |
|---|---|---|---|---|---|
| R1 | Entire evidence base is **single-sandbox, single-version** (ALM 26.1 SaaS) — every probe finding could differ on another instance or version (`data-model §7`, `api-ref §9` footnote) | M | H | Treat every probe-sourced client behavior as instance-specific until re-verified; design the write-safety component and metadata layer to be data-driven, not hardcoded to this sandbox's quirks | Re-run the write-probe script suite against a second ALM 26.1 project/instance if one becomes available (before hardening any single-sandbox finding into a permanent assumption) |
| R2 | **SaaS-flavored deployment** (Customer Admin role, `customers/*` family) may not represent on-prem behavior for session timeout, XSRF enforcement, or error envelope shape (`api-ref §1`, wave1-01 UNVERIFIED #8) | M | M | Document every session/auth finding as "confirmed on this SaaS sandbox," not "confirmed on ALM in general"; keep the session manager's timeout/keepalive values configurable, not baked in | Any deployment to an on-prem target triggers a re-verification pass on §2 auth findings |
| R3 | **Sanitizer allowed-HTML whitelist is deployment-specific** (`sanitizer-whitelist.xml`, no universal subset — `api-ref §7`) — Alt-ALM's rich-text editor could offer markup this instance's sanitizer silently strips on another deployment | M | M | Canonicalized round-trip contract test (test-strategy.md §4 item #4) run per target deployment before trusting the editor's allowed-markup set; never assume the probed subset transfers | New deployment target; sanitizer-related support report of unexpected content loss |
| R4 | **Fast_Run synthesis is a side effect of `PUT test-instances/{id}.status`, not a designed run-creation API** (`data-model §2.9`) — a future ALM release could change or remove this behavior, breaking the only confirmed run-creation path | L | H | Isolate the Fast_Run call behind one component so a break is a single-point fix; contract test (test-strategy.md §4 item #6) runs every phase-gate and on every upgrade to the target instance | Any ALM version upgrade on the target deployment; contract-test failure on the Fast_Run flow |
| R5 | **Deterministic `Fields`-array field-order requirement is undocumented server behavior** (`api-ref §3.2`) — root cause `UNVERIFIED` (plausibly positional processing), could change silently in a future build | L | H | Field-order regression test (unit + contract, test-strategy.md §2/§4 item #1) guards every entity-write shape; never rely on this order being permanent without re-verification after any server upgrade | Any 500 `Object.hashCode()`/`FieldEntry.getName()` NPE-style error reappearing after a previously-passing deploy |
| R6 | **HTTP 500 on a write may still have committed the row** (`api-ref §3.3`, one confirmed silent commit in probing) — any careless retry-on-error logic risks duplicate records | M | H | Write-safety component enforces "5xx = verify by query, never assume failure" universally, with no per-call opt-out (D7); mocked contract test (test-strategy.md §4 item #2) | Any duplicate-record report correlated with a prior 500 response |
| R7 | **Entity audit/history coverage is confirmed partial** — only status-field changes are logged; creates and rich-text/memo PUTs produce no audit entry (`probe log` Probe 4 §10) — undermines any history UI or generator provenance claim built on ALM's own audit trail | H | M | Never present the History tab as complete; Alt-ALM's own change-tracking (app-level, not ALM's audit trail) is the source of truth for full provenance where needed; UI copy states the caveat explicitly (P6 exit criteria) | Any user-facing complaint that "History doesn't show my edit" — expected, not a bug, but must be documented |
| R8 | **Multipart client-library compatibility is server-body-parsing-sensitive** — a PowerShell `-Form` constructor produced a body the server rejected while a hand-built body worked (`api-ref §6.6`, D2) — whatever HTTP client the BFF ultimately uses could hit the same class of failure | M | H | Multipart construction is integration-tested against the real sandbox server, not mocked, before shipping the image-embed feature (test-strategy.md §4 item #3); D2 names this risk explicitly regardless of stack choice | Any 201-expected multipart upload returning an opaque parse error in CI or production |
| R9 | **`step-parameters` has no confirmed REST creation path at all** (5 failed attempts, 2 rounds — `data-model §6`), **and the OTA fallback is now confirmed unreachable on this deployment** — the client side works (32-bit, per-user-registered 26.1 client) but the server's SSO front door 302-redirects the OTA handshake and every documented bridge failed (`live-probe-log.md` Probe 7) | H (gap confirmed; OTA fallback also confirmed blocked) | H (feature has no fallback on this deployment — raised from M) | Generator and UI scope parameterized-step *value recording* out of v1 entirely, with no fallback on this deployment; P6 OTA bridge stays optional/capability-flagged, mainline works without it (D3) | An on-prem or non-SSO ALM instance becomes available — triggers re-testing OTA reachability and, if it connects, the P6 OTA-bridge language decision and implementation (`tdconnect.exe` itself was already supplied and is not the blocker — probe 7) |
| R10 | **BPT/Business Components is REST-blocked by license gating**, not just absence (`GET /components` → 403 `operation-forbidden`, `data-model §6.7b`), **and its only candidate fallback (OTA) is now confirmed unreachable on this deployment** (`live-probe-log.md` Probe 7) | M | M (raised from L — BPT is a small feature surface, but it now has zero implementation path here, not just a license question) | Treat BPT as OTA-candidate-only per the matrix; on this deployment that candidate route is blocked, so BPT authoring is out of scope until a reachable OTA target exists — do not assume OTA COM access would bypass the license gate even then, verify separately once the bridge is reachable | An on-prem or non-SSO ALM instance becomes available and OTA connects; then attempt BPT via OTA and check for an equivalent license-forbidden response |
| R11 | **`alm-web` dialect body shape is entirely unprobed** (42 of 1,111 ops advertise it, `api-ref §3.5`) — Alt-ALM's grid/grouping UI could be built against a wrong assumption about this richer schema | L | L | P1's deferred probe settles the shape before any server-side group-by is implemented; client-side aggregation is the safe fallback already planned | P1 deferred-probe result |
| R12 | **Mail POST body shape is undocumented and confirmed failing** (4/4 attempted shapes, `api-ref §9`) — any plan to use ALM's own mail feature is blocked until this is solved or abandoned | L (Alt-ALM already plans to send its own mail) | L | Default design already routes Alt-ALM's own mail rather than `POST .../mail` (`matrix #198`); P6 deferred probe is best-effort, not load-bearing | P6 deferred-probe result; low priority to revisit |
| R13 | **Workflow-script bypass on REST writes is by design** (`CLIENT_TYPES_BYPASS_REST_WF`, `api-ref §6.8`) — every value a workflow script would have derived, validated, or blocked in the stock client is silently absent for REST writes, a genuine data-quality risk if the BFF's own validation layer has gaps | H | H | BFF validation layer (P2) is built from runtime metadata (Required/Editable/List) as the explicit substitute; this is necessarily incomplete relative to arbitrary VBScript logic — document as a permanent, honest limitation, not a bug to eventually fix | Any data-quality issue traceable to a value the stock client's workflow scripts would have rejected |
| R14 | **`UsersList` fields degenerate to one value until users are seeded** (sandbox has 1 project user, 77 `UsersList`-typed fields across 11 entities — `data-model §6`) — any generator realism testing done before seeding will be misleadingly uniform | M | L | Automated seeding via SA API (`site-users` + project-attach, `api-ref §6.9`) is a P4 prerequisite step, not optional; run before any generator realism/distribution testing | Generator output review showing suspiciously uniform owner/detected-by distribution |
| R15 | **Temptation to use undocumented endpoints found in `resource-list`/Swagger mining** (e.g., SA `run-query` raw SQL, `api-ref §6.9`) for a shortcut — explicitly against the `CLAUDE.md` hard constraint | L | H (constraint violation, not just technical risk) | Any undocumented-but-valuable endpoint is a risk-register entry, never an implementation, per charter; code review checklist should flag any call to a path not in the documented Core/Deprecated/per-instance-Swagger surface | Any PR introducing a call to an endpoint absent from the documented surfaces |
| R16 | **Licence/permission differences on other instances** — some probes succeeded only because this sandbox's API key holds **Customer Admin** SA role (role-id 2, `api-ref §2.4`); a lower-privilege deployment could lose SA-dependent capabilities (user seeding, site-params, some metadata reads) | M | M | Document every SA-dependent feature (user seeding, site-param CRUD) as contingent on the service account's SA role; capability-flag these in the BFF so a lower-privilege deployment degrades gracefully rather than failing opaquely | Deployment against an instance where the configured API key lacks Customer Admin (or equivalent) role |
| R17 | **The OTA fallback is confirmed unreachable on the current target deployment** (`live-probe-log.md` Probe 7) — the 23 `OTA`-verdict feasibility-matrix rows and the `step-parameters` generator gap have **no working implementation path today**; the plan must not schedule any of them as deliverable work against this sandbox | H (confirmed) | H (23 features, ~11% of the matrix, effectively closed) | Do not schedule OTA-dependent features (feasibility-matrix `OTA` rows) in the phased plan against this deployment; keep the P6 OTA bridge strictly optional/capability-flagged (D3) and revisit scheduling only once a reachable instance exists | An on-prem or non-SSO ALM instance becomes available for re-testing |
| R18 | **OTA, if it ever becomes reachable, carries a real deployment/ops constraint** — it requires a **32-bit host process** (64-bit COM instantiation fails `REGDB_E_CLASSNOTREG`), a **per-user or machine COM registration of a version-matched client** (a stale machine-wide 12.53 registration silently shadowed the correct 26.1 client and produced "Invalid server response" until superseded), and **separate type-library registration** (`regsvr32 /i:user` has no `DllInstall` export; the typelib must be registered via `RegisterTypeLibForUser` or method calls fail `TYPE_E_ELEMENTNOTFOUND` against a stale typelib) (`live-probe-log.md` Probe 7) | M (relevant only once/if a reachable target exists) | M (ops complexity for the sidecar host, not a functional blocker) | Document these as hard prerequisites in ADR 0003 / the OTA bridge's ops runbook before any future bridge implementation: 32-bit host process, version-matched per-target COM+typelib registration, elevation/GUI install avoided via the documented per-user registration workaround | Any future work item to stand up the OTA bridge sidecar |
