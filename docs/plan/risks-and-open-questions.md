| R18 | **OTA carries a real deployment/ops constraint, now proven necessary rather than hypothetical** — it requires a **32-bit host process** (64-bit COM instantiation fails `REGDB_E_CLASSNOTREG`), a **per-user or machine COM registration of a version-matched client** (a stale machine-wide 12.53 registration silently shadowed the correct 26.1 client and produced "Invalid server response" until superseded), and **separate type-library registration** (`regsvr32 /i:user` has no `DllInstall` export; the typelib must be registered via `RegisterTypeLibForUser` or method calls fail `TYPE_E_ELEMENTNOTFOUND` against a stale typelib) (`live-probe-log.md` Probe 7, reconfirmed Probe 8). **Probe 8 adds**: the client must be **ALM's own deployed client** copied from `%LOCALAPPDATA%\HP\ALM-Client\<version>\`, not a payload hand-extracted from the installer — the Probe 7 failure was traced to exactly that substitution, not to the server | M (relevant once the sidecar is built) | M (ops complexity for the sidecar host, not a functional blocker) | Document these as hard prerequisites in ADR 0003 / the OTA bridge's ops runbook: 32-bit host process, version-matched per-target COM+typelib registration sourced from ALM's own deployed client, elevation/GUI install avoided via the documented per-user registration workaround | Any future work item to stand up the OTA bridge sidecar |
| R19 | **Field metadata `editable:false`/`required:false` does not describe what a write needs** (`api-ref §3.6`, `live-probe-log.md` Probe 9 §9.3) — `POST test-parameters` omitting `ref-count` 500s as `"missing required field TP_REF_COUNT"` even though metadata reports it `editable:false, required:false`.
